# Виправлення системи обмежень підписки

## Дата: 2 травня 2026 р.

## Проблема
При базовій версії (BASIC tier) обмеження на створення складів не працювали правильно:
- Користувач міг створити 11-ий склад при ліміті 10
- Після видалення одного складу можна було знову створити новий
- Обмеження рахувались **тільки для конкретного підрозділу (unit_id)**, а не для всього тенанта

## Причина
Система підраховувала ресурси окремо для кожного підрозділу, а не для всього тенанта. Це дозволяло обходити ліміти, створюючи ресурси в різних підрозділах.

### Приклад проблеми:
```sql
-- Старий запит (неправильний)
SELECT COUNT(*) FROM warehouses WHERE unit_id = $1

-- Якщо у тенанта є підрозділи: HQ (id=1), Branch1 (id=2), Branch2 (id=3)
-- То можна було створити:
-- - 10 складів для HQ
-- - 10 складів для Branch1  
-- - 10 складів для Branch2
-- Всього: 30 складів замість 10!
```

## Рішення

### Backend виправлення

Оновлено всі функції перевірки лімітів у `millog_backend/internal/services/limitation_service.go`:

1. **CheckWarehouseLimit** - обмеження складів
2. **CheckResourceLimit** - обмеження ресурсів
3. **CheckUserLimit** - обмеження користувачів
4. **CheckVehicleLimit** - обмеження транспорту

Тепер кожна функція використовує рекурсивний SQL-запит для підрахунку ресурсів **для всього тенанта**:

```sql
WITH RECURSIVE tenant_units AS (
    -- Знаходимо всі підрозділи, пов'язані з поточним unit_id
    SELECT id, parent_id, tenant_id
    FROM units
    WHERE id = $1
    
    UNION ALL
    
    SELECT u.id, u.parent_id, u.tenant_id
    FROM units u
    JOIN tenant_units tu ON u.id = tu.parent_id
    WHERE tu.parent_id IS NOT NULL
),
root_tenant AS (
    -- Знаходимо кореневий тенант
    SELECT COALESCE(tenant_id, id) as tenant_root_id
    FROM tenant_units
    WHERE parent_id IS NULL
    LIMIT 1
),
all_tenant_units AS (
    -- Отримуємо всі підрозділи цього тенанта
    SELECT u.id
    FROM units u, root_tenant rt
    WHERE u.tenant_id = rt.tenant_root_id OR u.id = rt.tenant_root_id
)
SELECT COUNT(*)
FROM warehouses w
WHERE w.unit_id IN (SELECT id FROM all_tenant_units)
```

## Тестування

### Як перевірити виправлення:

1. **Створіть 10 складів на базовому тарифі**
   - Всі повинні успішно створитись

2. **Спробуйте створити 11-ий склад**
   - Повинна з'явитись помилка з кнопкою "Оновити тариф"
   - При натисканні на кнопку - перехід на `/billing`

3. **Видаліть один склад**
   - Тепер у вас 9 складів

4. **Створіть 2 нових склади**
   - Перший повинен створитись (буде 10)
   - Другий повинен заблокуватись з помилкою

5. **Перевірте різні підрозділи**
   - Створіть склад для підрозділу A (9 складів загалом)
   - Створіть склад для підрозділу B (10 складів загалом)
   - Спроба створити склад для підрозділу C повинна бути заблокована

## Статус коду помилки

Backend повертає **HTTP 402 Payment Required** при досягненні лімітів, що є семантично правильним статусом для обмежень підписки.
