# Технічна документація Omnilog

## 1. Загальний опис проєкту

Omnilog — це багатокористувацька логістична система для обліку майна, управління заявками, складами, перевезеннями, автопарком і підрядницькими запитами між організаціями. З коду видно, що система орієнтована на операційний контроль запасів, руху ресурсів, транспорту та виконавської дисципліни.

Основні можливості: управління користувачами й ролями, ієрархія підрозділів, складський облік, видача майна, аудит інвентаризації, заявки на постачання, Smart Dispatch, рейси та маршрутні листи, GPS-відстеження, контроль пального, техобслуговування, аналітика, Excel/PDF-звіти, сповіщення та керування організаціями платформи. Система розроблена для організацій з багаторівневою структурою, окремо підтримує платформного адміністратора, внутрішніх співробітників та зовнішніх підрядників.

## 2. Технологічний стек

**Frontend:** React + TypeScript + Vite. `react-router-dom` використовується для маршрутизації, `recharts` для візуалізації аналітики, `react-hot-toast` для системних повідомлень, `html2canvas` + `jspdf` для формування клієнтських PDF, `html5-qrcode` для QR-сканування під час інвентаризації. Такий стек дає швидкий SPA-інтерфейс з розділенням доступу за ролями й тарифами.

**Backend:** Go + Gin. Gin використовується як HTTP-фреймворк, `pgx/pgxpool` — для роботи з PostgreSQL, `golang-jwt/jwt/v5` — для JWT, `bcrypt` — для хешування паролів, `godotenv` — для ENV-конфігурації, `gofpdf` — для серверного PDF накладних, `excelize` — для Excel-експорту та імпорту, `go-qrcode` — для генерації QR-кодів.

**База даних:** PostgreSQL. Вона використовується як транзакційне сховище для всіх доменних сутностей і підтримує row-level security для ізоляції tenant-даних. Схема створюється програмно в `millog_backend/internal/database/migrate.go`.

**Інші бібліотеки та сервіси:** SMTP для інвайтів, скидання пароля та SLA-сповіщень; публічний OSRM API для розрахунку відстаней рейсів, якщо їх не передано з фронтенду. Ознак використання черг, кешу або зовнішнього файлового сховища в переглянутому коді не знайдено.

## 3. Архітектура системи

Система побудована як monorepo з двома застосунками: `millog_frontend` і `millog_backend`. На бекенді використано послідовність `handler -> service -> repository -> PostgreSQL`, що ізолює HTTP-рівень від бізнес-логіки і доступу до даних. На фронтенді сторінки викликають API-клієнт, використовують контексти (`AuthContext`, `GPSContext`) та захищені маршрути.

Взаємодія відбувається за схемою Frontend → REST API → сервіси → PostgreSQL. Фронтенд надсилає JWT access token у заголовку `Authorization`, а бекенд додатково звіряє поточний статус, роль, unit і tenant користувача безпосередньо в БД на кожному захищеному запиті. Для multi-tenancy tenant-контекст передається далі в `context.Context` і використовується репозиторіями та RLS.

Модулі організовані за доменами: автентифікація, користувачі, підрозділи, склади, інвентар, заявки, підрядники, автопарк, GPS, аналітика, аудит, білінг/тарифи, сповіщення та платформне адміністрування.

## 4. Структура бази даних

Основні таблиці: `tenants`, `users`, `units`, `resource_categories`, `resources`, `resource_assignments`, `supply_requests`, `warehouses`, `shipments`, `shipment_items`, `shipment_refuels`, `vehicles`, `fuel_records`, `maintenance_records`, `vehicle_driver_history`, `contractor_requests`, `contractor_memberships`, `gps_locations`, `geofences`, `geofence_alerts`, `notifications`, `audit_logs`, `inventory_checks`, `inventory_check_items`, `invite_tokens`, `refresh_tokens`.

Ключові зв’язки: користувачі належать до `tenants` і можуть бути прив’язані до `units`; ресурси належать категоріям, підрозділам і складам; заявки, транспорт, склади, рейси, пальне, GPS-дані й журнали аудиту також мають `tenant_id`; рейс пов’язує склади, транспорт і набір позицій; записи ТО й пального пов’язані з транспортом; підрядники співпрацюють з організаціями через `contractor_memberships`.

Multi-tenancy реалізовано явно: майже всі бізнес-таблиці мають `tenant_id`, для них створено індекси та RLS-політики `tenant_isolation`. `SYSTEM_ADMIN` працює без tenant-обмеження, а `CONTRACTOR` навмисно має `tenant_id = NULL`, щоб бачити крос-tenant дошку відкритих підрядницьких задач; при цьому право взяти задачу обмежується таблицею `contractor_memberships`.

## 5. Реалізований функціонал

**Автентифікація та користувачі.** Підтримуються login, refresh, logout, bootstrap першого адміністратора, реєстрація підрядника, створення tenant-а, інвайтний сценарій встановлення пароля, зміна профілю, зміна пароля, блокування та розблокування користувачів. Ролі і допустимі переходи ролей описані централізовано; бекенд перевіряє їх окремо від UI.

**Організації та підрозділи.** Є окремі сутності `tenants` і `units`, платформа підтримує системного адміністратора з крос-tenant доступом і support-mode через заголовок `X-Support-Tenant-ID`. Для підрозділів реалізовано ієрархію, створення, зміну керівника, побудову доступної ієрархії та role-based видимість.

**Складський облік.** Реалізовано категорії, ресурси, залишки, мінімальні пороги, вагу, ціну, QR-коди, видачу майна користувачам, списання, видимість майна користувача, рапорти по виданому майну, аудит інвентаризації та імпорт Excel. Частина операцій захищена тарифами.

**Склади та логістика.** Є довідник складів, збереження координат, прив’язка ресурсів і транспорту до складів, створення рейсів між складами, реєстрація відправлення/приймання, дозаправка в дорозі, історія рейсів, особистий список рейсів для водія, PDF-накладна та розрахунок GPS-відстані.

**Заявки на постачання.** Реалізовано створення, перегляд, затвердження, відхилення, скасування та детальний перегляд заявок. Для PRO-тарифу є Smart Dispatch: попередній розрахунок оптимального розподілу заявок по транспорту і подальше підтвердження з формуванням окремих рейсів.

**Підрядницький модуль.** Є окрема дошка `contractor_requests`, де внутрішні користувачі створюють зовнішні запити, а підрядники можуть брати їх у роботу і доставляти. Після доставки внутрішня сторона може прийняти на баланс, відхилити або скасувати; право роботи з конкретною організацією регулюється `contractor_memberships`.

**Автопарк і пальне.** Реалізовано облік транспорту, статусів, водіїв, історії призначень, технічного обслуговування, планового ТО, файлів актів робіт, записів пального та виявлення аномалій. Доступ до файлів ТО надається лише через захищений endpoint з перевіркою tenant-приналежності документа.

**GPS і геозони.** Підтримуються пінги водія, визначення активного рейсу, збереження GPS-локацій, карта автопарку, траєкторія руху, геозони, сповіщення про порушення геозон і статус флоту. Частина функцій доступна лише на PRO.

**Аналітика, аудит і сповіщення.** Є аналітичний дашборд, KPI, прогноз попиту, прогнозне ТО, виявлення аномалій пального, Excel-експорт по складах і пальному, SLA-моніторинг та журнал аудиту. Система сповіщень підтримує список, лічильник непрочитаних, позначення прочитаного та масове очищення.

## 6. Основні технічні рішення

Ключове рішення — багаторівневий захист multi-tenancy: `tenant_id` у таблицях, передача tenant-контексту через middleware та окремий RLS-рівень у PostgreSQL. Це зменшує ризик витоку даних навіть при помилці на рівні запиту.

Рольова модель винесена в окремі константи на фронтенді й бекенді, а критичні перевірки виконуються на сервері. Такий підхід дозволяє гнучко керувати доступом у UI, не покладаючись на нього як на механізм безпеки.

Логістичні сценарії реалізовані транзакційно: створення рейсів, видача майна, підтвердження Smart Dispatch, дозаправка в рейсі та приймання ресурсів виконуються через сервіси та репозиторії з роботою в БД. Це важливо для цілісності залишків, статусів і пов’язаних журналів.

## 7. Безпека

Автентифікація побудована на JWT access token та refresh token. Access token живе 24 години і на фронтенді зберігається лише в пам’яті, refresh token використовується через `httpOnly` cookie; паролі хешуються через `bcrypt`, а активація користувача виконується інвайт-токеном.

Авторизація виконується через middleware `RequireAnyRole`, `RequireTenant`, `RequireSystemAdmin` та `RequireSubscriptionTier`. На кожному захищеному запиті бекенд перечитує з БД статус користувача, tenant, роль і unit, тому зміна прав або деактивація організації застосовується без очікування завершення JWT.

Захист API включає CORS-обмеження, security headers, rate limiting для auth endpoint-ів, перевірку статусу організації, контроль доступу до файлів ТО, аудит дій і логування несанкціонованого доступу до платних функцій. Ізоляція організацій забезпечується tenant-контекстом і RLS; для `CONTRACTOR` використано окрему модель глобального доступу з додатковим пер-tenant погодженням.

## 8. Аналітика та звіти

Аналітика формується на бекенді SQL-запитами та агрегатами по `supply_requests`, `resources`, `shipments`, `shipment_refuels`, `vehicles`, `fuel_records`, `maintenance_records` і складах. Реалізовано базовий dashboard, KPI по SLA/TCO/ризиках, прогноз попиту за історією заявок, прогнозне ТО за пробігом і датами сервісу, а також оцінку аномалій пального за 90-денним вікном.

PDF-звіти реалізовано у двох варіантах. Для маршрутних листів PDF генерується на бекенді через `gofpdf` на основі даних рейсу та позицій відвантаження. Для аналітичного звіту PDF збирається на фронтенді: прихований HTML-шаблон рендериться в canvas через `html2canvas`, після чого експортується через `jsPDF`.

Excel-звіти (`inventory`, `fuel`) формуються на бекенді через `excelize`. Дані для них беруться безпосередньо з репозиторіїв і повертаються як файли для завантаження.

## 9. Структура проєкту

`millog_frontend/src/pages` містить бізнес-сторінки: авторизація, інвентар, заявки, склади, підрозділи, автопарк, аналітика, GPS, аудит, білінг, платформа, профіль, термінал і підрядницькі сценарії. `src/components` містить спільні UI-компоненти, `src/api` — централізований API-клієнт, `src/contexts` — глобальні стани сесії та GPS, `src/constants` — ролі, дії та feature-gate правила.

`millog_backend/internal/handlers` містить HTTP-обробники, `services` — бізнес-логіку, `repositories` — доступ до PostgreSQL, `models` — доменні структури, `middleware` — безпеку, tenant- і тарифні перевірки, `database/migrate.go` — джерело поточної схеми БД. `main.go` збирає залежності, запускає міграції й реєструє маршрути.

Окремих ADR, генераторів API-клієнта або автоматично згенерованої документації з коду у переглянутій частині проєкту не виявлено.

## 10. Висновок

Сильні сторони реалізації: чітке доменне розділення бекенду, багаторівнева tenant-ізоляція, детальна рольова модель, транзакційна логістика, інтеграція складського, транспортного й аналітичного контурів у межах однієї системи. Проєкт уже покриває не лише облік, а й операційне планування, моніторинг і контроль виконання.

Подальший розвиток логічно спрямувати на поглиблення білінгу, централізовану серверну генерацію всіх офіційних звітів, асинхронну обробку важких задач, зовнішні інтеграції GPS/ERP та автоматизоване тестове покриття. Якщо певні нефункціональні вимоги на кшталт CI/CD, резервного копіювання або observability не видно з коду, їх стан у цій документації не визначається.
